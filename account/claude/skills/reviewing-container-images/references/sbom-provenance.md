# SBOM and provenance checks

Only what an image reviewer checks. Paraphrased from the primary sources named per section.

## NTIA SBOM minimum elements

Source: The Minimum Elements For a Software Bill of Materials (SBOM), US Department of Commerce /
NTIA, July 12, 2021. https://www.ntia.doc.gov/files/ntia/publications/sbom_minimum_elements_report.pdf

Three areas: data fields, automation support, practices and processes.

**Data fields** (per component). Check each is present:

| Field | What to check in an image SBOM |
|---|---|
| Supplier Name | Originator of the component. Often blank for distro packages. Note blanks. |
| Component Name | Present for every package. |
| Version of the Component | Matches the installed version the scanner reports. |
| Other Unique Identifiers | CPE, SWID, or PURL. PURL is what lets you match scanner rows to SBOM rows. |
| Dependency Relationship | Direction of inclusion. Many image SBOMs list a flat package set with no relationships. Say so. |
| Author of SBOM Data | Who generated the data (the tool or party), not who wrote the software. |
| Timestamp | When the SBOM was assembled. An SBOM older than the image digest it claims to describe is stale. |

**Automation support.** Machine-readable in SPDX, CycloneDX, or SWID tags.

**Practices and processes.** The ones a reviewer checks:

- Frequency: a new build needs a new SBOM. Match the SBOM to the image digest, not the tag.
- Depth: at minimum all top-level components, with enough detail to find transitive ones.
- Known unknowns: the SBOM must say where the dependency graph is incomplete. Default reading is
  "incomplete" unless the author states otherwise. Treat a missing component as unknown, not absent.
- The other three (distribution and delivery, access control, accommodation of mistakes) matter for
  supplier contracts, rarely for a single image review.

The same report describes VEX (Vulnerability Exploitability eXchange): a supplier statement that a
product is or is not affected by a given vulnerability. A VEX "not affected" is supplier data, tier F
in the skill's evidence tiers, and should name its author and date.

## SLSA build levels

Source: SLSA v1.2, Build track basics, https://slsa.dev/spec/v1.2/build-track-basics. The v1.1
levels page (https://slsa.dev/spec/v1.1/levels) carries the same Build L0 to L3 table. v1.2 also adds
a Source track, not covered here.

| Level | Requirement | Protects against |
|---|---|---|
| Build L0 | None | Nothing |
| Build L1 | Provenance exists showing how the package was built | Mistakes. Trivial to forge. |
| Build L2 | Provenance signed and generated by a hosted build platform. Consumer validates authenticity. | Tampering after the build |
| Build L3 | Hardened build platform: runs isolated from each other, signing secrets not reachable by user-defined build steps | Tampering during the build |

What a reviewer checks:

- Is there provenance for this digest at all (attestation attached to the image or in the registry)?
- Is it signed, and by a hosted build platform identity you can name? Unsigned provenance is L1 at most.
- Does the provenance source repository and commit match what the requester says the image is?
- State the level you can evidence, not the level the producer claims.
