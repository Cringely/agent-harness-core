# NIST SP 800-190 risks and countermeasures

Source: NIST Special Publication 800-190, Application Container Security Guide, September 2017.
https://doi.org/10.6028/NIST.SP.800-190 (PDF read from nvlpubs.nist.gov). US government work, not
subject to copyright in the United States. Section numbers are exact. Text is paraphrase, not quotation.

Each 3.x risk has a 4.x countermeasure with the same last digits. Cite as "SP 800-190 3.1.2" or "4.1.2".

## 3.1 / 4.1 Image

| No. | Risk (section 3) | Countermeasure (section 4) |
|---|---|---|
| 3.1.1 / 4.1.1 | Image vulnerabilities. Images are static, so components go stale and must be fixed by rebuild and redeploy, not in place. | Container-aware scanning across build, registry and runtime, covering all layers, with policy gates (for example a CVSS threshold). |
| 3.1.2 / 4.1.2 | Image configuration defects, such as no non-root user or an SSH daemon in the image. | Validate config against vendor and third-party practice, report compliance centrally, optionally block noncompliant images, use minimal trusted base layers. Never enable SSH or other remote shells in containers. |
| 3.1.3 / 4.1.3 | Embedded malware, often from third-party base layers of unknown provenance. | Monitor all images with signature sets and behavioral heuristics. |
| 3.1.4 / 4.1.4 | Embedded clear text secrets (passwords, connection strings, SSH or X.509 private keys) readable by anyone with the image. | Keep secrets out of images, inject at runtime from orchestrator or enterprise secret stores, scope each secret to the containers that need it, encrypt at rest and in transit. |
| 3.1.5 / 4.1.5 | Use of untrusted images from external sources. | Central allowlist of trusted images and registries, cryptographic signatures, enforcement that hosts run only approved images, signature validation before run, ongoing maintenance. |

## 3.2 / 4.2 Registry

| No. | Risk | Countermeasure |
|---|---|---|
| 3.2.1 / 4.2.1 | Insecure connections to registries expose image contents and credentials, and allow tampered images. | Connect to registries only over encrypted channels between trusted endpoints. |
| 3.2.2 / 4.2.2 | Stale images in registries raise the chance of deploying a known-vulnerable version. | Prune unsafe images, deploy by immutable version names. If using a `latest` tag, ensure it really is current. |
| 3.2.3 / 4.2.3 | Insufficient authentication and authorization. A compromised registry compromises downstream hosts. | Authenticate all access to sensitive images and all writes, scope push rights per repository, audit writes and sensitive reads, push only after scan and compliance checks. |

## 3.3 / 4.3 Orchestrator

| No. | Risk | Countermeasure |
|---|---|---|
| 3.3.1 / 4.3.1 | Unbounded administrative access across teams and apps. | Least-privilege, role-scoped access to hosts, containers and images. |
| 3.3.2 / 4.3.2 | Unauthorized access through separate, weakly managed orchestrator accounts, and unencrypted data volumes. | Tight control of cluster-admin accounts, MFA, SSO to the existing directory, container-compatible data-at-rest encryption. |
| 3.3.3 / 4.3.3 | Poorly separated inter-container network traffic, opaque overlay networks, apps of mixed sensitivity on one network. | Separate virtual networks by sensitivity level, with few well-defined interfaces between them. |
| 3.3.4 / 4.3.4 | Mixing of workload sensitivity levels on one host. | Pin workloads to host sets by sensitivity, one sensitivity level per host kernel. |
| 3.3.5 / 4.3.5 | Orchestrator node trust: rogue nodes joining, shared keys, unauthenticated control traffic. | Secure node introduction, persistent node identity, node inventory, resilience to single-node compromise, mutually authenticated and encrypted cluster traffic. |

## 3.4 / 4.4 Container

| No. | Risk | Countermeasure |
|---|---|---|
| 3.4.1 / 4.4.1 | Vulnerabilities within the runtime software, including container escape. | Monitor and patch the runtime quickly, deploy only to maintained runtimes. |
| 3.4.2 / 4.4.2 | Unbounded network access from containers, especially egress, invisible to non-container-aware tools. | Control egress at network borders and with app-aware filtering that knows inbound ports and process-port bindings and flags anomalies. |
| 3.4.3 / 4.4.3 | Insecure container runtime configurations: widened syscalls, privileged mode, sensitive host mounts. | Automate compliance with runtime config standards (the CIS Docker Benchmark is named), use SELinux or AppArmor, keep at least the runtime's default seccomp profile. |
| 3.4.4 / 4.4.4 | App vulnerabilities in the containerized software itself. | Container-aware runtime profiling that flags unexpected processes, syscalls, file writes, new network listeners and outbound traffic. Run with a read-only root filesystem. |
| 3.4.5 / 4.4.5 | Rogue containers, unplanned and unscanned. | Separate environments with role-based deployment control, per-user audit trail of container creation, baseline checks before an image may run. |

## 3.5 / 4.5 Host OS

| No. | Risk | Countermeasure |
|---|---|---|
| 3.5.1 / 4.5.1 | Large host attack surface. | Container-specific minimal OS where possible, otherwise harden per NIST SP 800-123, run only containers on the host, scan and patch including the kernel. |
| 3.5.2 / 4.5.2 | Shared kernel gives weaker isolation than a hypervisor. | Group by sensitivity and do not mix containerized and non-containerized workloads on one host. |
| 3.5.3 / 4.5.3 | Host OS component vulnerabilities (crypto libraries, kernel) affect every container. | Track and patch all host components, especially kernel and runtime, or redeploy updated hosts. Operate hosts immutably. |
| 3.5.4 / 4.5.4 | Improper user access rights: direct host logins to manage containers. | Audit OS authentication, monitor login anomalies, log privilege escalation. |
| 3.5.5 / 4.5.5 | Host OS file system tampering through sensitive host mounts. | Minimal filesystem permissions, persist only to dedicated volumes, never mount sensitive host directories, monitor and block violating mounts. |

4.6 covers hardware countermeasures (measured boot, TPM-rooted trust). Rarely in scope for an image review.

## Mapping hints for this skill

- Kernel-header CVEs in an image are a 3.5.3 host-patching signal, not a 3.1.1 image finding.
- A listener or sshd found in an image is 3.1.2 (and 3.4.4 once running).
- Privileged mode, docker.sock, sensitive host mounts map to 3.4.3 and 3.5.5.
- Quarantine in a registry addresses 3.2.2. It does nothing for containers already running (3.4).
