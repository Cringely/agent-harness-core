# Harness Layering Plan C: Layer Content Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fill the documents and physical layers that Plan A built the machinery for. That means the two layer rule files, an office toolchain probe whose result a session can read, the move of layer skills out of the account layer into core so a project gets them only when it records the layer, `document-skills` loading at project scope only, and a ruling on the agent definitions the spec assigns to layers.

**Architecture:** Rule content lands as `core/claude/rules/documents.md` and `core/claude/rules/physical.md`, registered in `core/claude/rules/layers.json`, and Plan A's installer copies them unchanged. The office probe reuses Plan A's dependency preflight: new `documents` entries in `core/claude/deps.json`, and `Invoke-DepsPreflight` hands its per-tool results back so `Install-Harness.ps1` can write them to the sidecar. Skills reuse the `core/claude/skills/` install path that PR #341 adds, with a new `skills` map in `layers.json` deciding which project receives each one. The account copies are removed at the source, exported, and retired on receivers through Plan A's retire list. That list already retires a skill by its `SKILL.md` and refuses a directory entry the receiver holds. It learns to refuse every other `skills/` entry.

**Tech Stack:** Bun and TypeScript (`bun test`), PowerShell 7 with Pester 5 for the installers, Python 3 standard library for the not-ai gate.

**Spec:** `docs/superpowers/specs/2026-11-11-harness-layering-design.md` (tracking issue #310). Plan A: `docs/superpowers/plans/2026-11-11-harness-layering-plan-a-foundation.md`. Field reports: #294 (physical build, closed with its physical items assigned here) and #308 (analysis brief).

Carried from Plan A, still binding:

- Rule and skill text copied into `core/` or `test/fixtures/` comes from the exported, redacted `account/claude/` tree at a commit, never from `~/.claude` directly.
- Commits use `git -c user.name=Cringely -c user.email=Cringely@users.noreply.github.com commit ...`, with no attribution trailer or session link. A commit message never mentions reviews or findings.
- Every isolated write dispatch carries a `BASE-SHA: <sha>` line. The agent compares it with its worktree HEAD before touching a file and aborts on a mismatch. Worktree agents commit only, and the coordinator pushes.
- Tests: `bun test` from the repo root, from the Bash tool. Pester as `pwsh -NoProfile -File install/<name>.Tests.ps1` from the PowerShell tool, never bare `Invoke-Pester` (it exits 0 on failure).

- Every matcher that reads a repo file is CRLF-agnostic: split on `/\r?\n/` in TypeScript and normalize `"\r\n"` to `"\n"` on both sides before comparing text.
- Timestamps are UTC at the point of formatting (`Get-Date -AsUTC`, `toISOString()`).
- Layer names are exactly `code`, `documents`, `physical`. The kernel is implied and never listed.
- A probe that cannot answer fails closed: the tool counts as absent.
- One PR per task group. The App reviewer is the merge gate. Every PR body carries a `Docs: README ...` verdict line. Rule-file and README prose follows `writing-style.md`.
- Redirect `git show` output to a file from Git Bash, never from PowerShell, which re-encodes it.

```markdown
# Documents and Analysis Projects

This project's deliverables are documents, decks, spreadsheets or analyses that people read. The status cadence, the audience and the default length budget are project settings in `project-settings.md` beside this file. This file carries the working rules around them.

## Every prose brief carries a length budget

A brief for a prose deliverable names its budget in words or pages. Take it from the operator's request, else from the project's length budget setting, else ask once. The writer stays within it. A checker that reports something missing also names what to cut to make room for it, or the finding is dropped. After the writer finishes, count the words in the produced file. Over budget sends it back to the writer once, with the count and the budget. A second miss goes to the operator rather than into a third round.

## An edited generated file belongs to the operator

Before a generator writes over an existing `.docx`, `.xlsx`, `.pptx` or `.pdf`, check the decision log for an entry naming that file as operator-mastered. When there is none and the file is newer than its last generation, ask before writing. Once the operator has edited a generated file, that file is the master. Changes go into it directly, never into its markdown source followed by a regeneration. Record the switch in the decision log with the file path, `master: operator` and the date, so the next session does not depend on anyone remembering it.

## Reconcile numbers against the delivered file

Number reconciliation reads the file as delivered: the text of the `.docx` (from its XML or through Word), the PDF text, or the spreadsheet cells. It does not read the markdown the file was generated from. It runs last, after the operator's final edit. A reconciliation that could only read the source says so in the close.

## Keep a numbers ledger and a human-check register

- The numbers ledger lives at `docs/numbers-ledger.md`, or at `numbers-ledger.md` in the project root when there is no `docs/` folder. It has one row per figure that appears in a deliverable: the value, its source file and location, and the UTC date it was taken. Reconciliation checks the deliverable against it.
- The human-check register lives at `docs/human-checks.md` on the same rule. It has one row per check a person ran: what was checked, who ran it by role, and the date. A check missing from the register is unknown, not skipped. Ask the operator before saying it did not happen.

## Size review to the decision

A method decision (which data, which model, what counts as a match) may go to a council. Prose review goes to one reviewer for one round, working against the length budget, under `bounded-review.md`. A council spent on prose review produces many outputs for one revision and adds length rather than removing it.
```

```markdown
# Physical and Hardware Projects

This project builds or specifies physical things: furniture, fixtures, enclosures, boards, cable harnesses. The expensive errors here are misread requirements and wrong parts rather than code bugs, so these rules sit in front of dispatch.

## Restate the requirement in physical terms before dispatch

Before a brief goes out, restate each requirement it carries in physical terms: which part, which axis or dimension, the unit, and whether the number is a floor, a ceiling or a target. When two readings of a requirement would change different parts, ask the operator which one is meant before dispatching. A misread requirement costs a full design, review and render cycle, which is far more than the question costs.

## A stated capacity is a floor with margin

A capacity the operator states (a vise opening, a load, a clearance, a current) is a floor to clear with margin, with every feature the operator asked for kept. When the current part cannot reach it comfortably, the smallest correct change is a different part, not shaved clearances or dropped features. In a project that also carries the code layer, this section governs physical capacity wherever `fix-quality.md` asks for the smallest change that restores the invariant.

## Rank evidence about goods

Evidence about a part, a material or a price ranks as follows, strongest first:

1. a field measurement by the operator
2. the manufacturer's spec sheet
3. a seller's listing image
4. a retailer's product page
5. a search snippet

Name the tier behind each figure you report. A snippet price or dimension is a lead to check, not a fact. A blocked or failed read (a 403, 429 or 503, or a template string where a price should be) is a failed fetch. Report it as "could not read it, tried X", never as "sold out" or "not listed".

## Parametric models carry self-checks with negative controls

A parametric model or generator script asserts the physical facts the design depends on: clearances, fits, travel, and that each part can be inserted and removed. Each check runs with a negative control, a deliberately broken input that must make it fail. A check whose negative control does not fire is not evidence, because it would also pass on a broken design.

## Offer a local git repository at the first real work

When this folder is not a git repository and the work starts producing files that change across versions (models, renders, cut lists, shopping lists), offer once to run `git init` here, local only, with no remote. It replaces copied version folders and parallel agents partitioning one file by row, and it lets the worktree gate isolate concurrent writers. Do not run it unasked.
```

const loaded = use < 0 ? undefined : ev.slice(use + 1).find((e) => e.type === "user" && textOf(e).startsWith(BASE));

if (runs.length === 0) out.push("GATE NOT RUN");
